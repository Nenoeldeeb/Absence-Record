# Data Model — 008 Duration-Based Scheduling

**Feature**: `specs/008-duration-based-scheduling`
**Spec**: [spec.md](./spec.md) · **Decisions**: [research.md](./research.md)

All times are `Int` minutes from midnight (00:00 = 0, 24:00 = 1440), matching the
existing codebase. All durations are minutes.

## New value types (domain)

These are **not** persisted. They are computed results.

### `PlannedSlot`

```kotlin
data class PlannedSlot(
    val studentId: Int,
    val studentName: String,
    val position: Int,      // 1-based
    val startMinutes: Int,  // block.start + (position - 1) * 10
    val endMinutes: Int     // startMinutes + 10
)
```

### `PlannedHour`

```kotlin
data class PlannedHour(
    val blockStartMinutes: Int,
    val blockDurationMinutes: Int,
    val slots: List<PlannedSlot>,          // in running order
    val maxStudents: Int                   // = blockDurationMinutes / 10
)
```

### `SlotConflict`

```kotlin
data class SlotConflict(
    val studentId: Int,
    val studentName: String,
    val slotStartMinutes: Int,
    val slotEndMinutes: Int,
    val busyStartMinutes: Int,
    val busyEndMinutes: Int
)
```

### `DroppedStudent`

```kotlin
data class DroppedStudent(
    val studentId: Int,
    val studentName: String,
    val reason: DropReason
)

enum class DropReason { ExceedsCapacity, SlotConflictsWithBusy }
```

### `HourReplanResult` — the two-phase confirm contract (D5)

```kotlin
sealed interface HourReplanResult {
    data class Applied(val removedStudentIds: List<Int>) : HourReplanResult

    data class NeedsConfirmation(
        val proposed: PlannedHour,
        val dropped: List<DroppedStudent>
    ) : HourReplanResult
}
```

`NeedsConfirmation` carries everything the confirm dialog needs — the resulting
running order via `proposed`, and the named drop list via `dropped` — so a
separate proposal type is not needed. The first call returns this **without
writing**; a second call with `confirmed = true` commits and returns `Applied`.

## Ordering algorithm (normative)

Single source of truth: `domain/services/LessonSlotPlanner.kt`. This is the
contract the implementation must satisfy; it is fully determined by the spec.

```
plan(blockStart, blockDuration, students: List<StudentInput>): PlannedHour

StudentInput = (studentId, studentName, busyAppointmentsOnWeekday)
```

**Step 1 — next relevant commitment** (FR-021)
For each student, the minimum `startMinutes` over their appointments with
`startMinutes >= blockStart`. Commitments ending before `blockStart` are ignored.
Students still inside an appointment at `blockStart` are *not* excluded here —
they are caught by step 4.

**Step 2 — sort** (FR-022, FR-023, FR-024, FR-025)

| Rank | Key | Direction |
|------|-----|-----------|
| 1 | next relevant commitment | ascending, `Int.MAX_VALUE` (i.e. none) sorts last |
| 2 | `studentName` | ascending, **case-insensitive and locale-independent** |
| 3 | `studentId` | ascending — guarantees total determinism |

Rank 3 exists so two students sharing a name can never produce an unstable order.

**Step 3 — assign slots** (FR-018, FR-019)
Position *n* (1-based) occupies `[blockStart + (n-1)*10, blockStart + n*10)`.
The final slot ends exactly at the block's end because the block's duration is a
multiple of 10 (FR-002).

**Step 4 — validate** (FR-026, FR-027, FR-028, FR-030)
For every student and every one of their appointments, test
`slotStart < busyEnd && slotEnd > busyStart`. Half-open: an appointment starting
exactly when the slot ends is **not** a conflict; one starting exactly when the
slot starts **is**. Collect every conflict rather than short-circuiting, so the
teacher sees all of them at once.

**Step 5 — capacity** (FR-003, FR-035)
If `students.size > blockDuration / 10`, the surplus (by the step-2 order) is
dropped — this is what makes "keep the first *N*" of FR-010 well-defined.

**Invariants the tests must assert**

1. `slots.size == min(students.size, maxStudents)`
2. Slot *n* starts at `blockStart + (n-1)*10`; the last ends at
   `blockStart + blockDuration`
3. Sorting is a pure function of the inputs — no dependence on input list order
4. No slot overlaps any of its student's appointments
5. Recomputing with identical inputs yields an identical `PlannedHour`

## Backup file shape

Full schema in [contracts/backup-file-format.md](./contracts/backup-file-format.md).

| Version | Block field | Read as |
|---------|-------------|---------|
| `3` (current, after this change) | `durationMinutes` | direct |
| `2` (previous) | `maxStudents` | `min(120, max(10, value * 10))` |
| legacy flat array | *(none)* | students only, no schedule |
| anything else | — | `StudentError.UnsupportedBackupVersion`, nothing written |

An entry carrying **both** `maxStudents` and `durationMinutes` is malformed and is
skipped and counted (FR-046).

## Import caps (FR-056…FR-059, D9)

| Constant | Value | Provenance |
|----------|-------|------------|
| `MAX_IMPORT_STUDENTS` | 10,000 | judgement call — flagged for confirmation |
| `MAX_IMPORT_HOURS` | 1,008 | derived: 7 days × 1440 min ÷ 10 min |
| `MAX_IMPORT_ASSIGNMENTS` | 12,096 | derived: `MAX_IMPORT_HOURS` × 12 max students |

Exceeding a cap skips and counts; it never aborts the import and is never
reported as a parse failure (FR-059).
